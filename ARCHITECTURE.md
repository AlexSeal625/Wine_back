# WINE Backend — Архитектура

Документ описывает архитектуру backend-сервиса `Wine_back`: сквозной пайплайн обработки запроса, границы слоёв внутри монолитного `main.py`, и детально — пять функциональных зон: нормализация фото, извлечение признаков, поиск по каталогу, извлечение карточки вина и дополнительные функции (лента, тестовые эндпоинты, устойчивость).

---

## 1. Пайплайн верхнего уровня

```
Клиент
  │  POST /api/recognize { image_base64 }
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. НОРМАЛИЗАЦИЯ ФОТО                                          │
│    Base64 → PIL.Image → letterbox под 640×640                 │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. ИЗВЛЕЧЕНИЕ ПРИЗНАКОВ                                        │
│    YOLO (детекция этикетки) → crop → DINOv2 (embedding 384-d) │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. ПОИСК ПО КАТАЛОГУ                                           │
│    FAISS top-5 → фильтрация по порогам → wine_id → slug       │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. ИЗВЛЕЧЕНИЕ КАРТОЧКИ                                         │
│    HTTP GET vino-svoe.ru/wines/{slug} → BeautifulSoup parse   │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
                    JSON-ответ клиенту
```

Все четыре зоны выполняются последовательно и синхронно внутри одного запроса — промежуточные результаты нигде не персистятся (ни в БД, ни в кэше), кроме отдельного TTL-кэша ленты (зона 5).

## 2. Границы слоёв

Несмотря на то что весь код физически находится в одном файле `main.py`, в нём чётко прослеживаются пять функциональных слоёв, различающихся ответственностью, входом/выходом и жизненным циклом:

| Слой | Инициализация | Состояние | Основные функции |
|---|---|---|---|
| **API-слой** | При старте FastAPI (`lifespan`) | Без состояния (stateless) | `recognize_wine`, `memory_wine`, `test_by_slug`, `get_feed` |
| **Нормализация** | — | Без состояния | декодирование Base64, `letterbox_preprocess` |
| **ML-слой (признаки)** | При импорте модуля (однократно, тяжёлые модели) | Модели в памяти процесса; сам вызов — без состояния | `run_ml_pipeline`, `get_dinov2_embedding` |
| **Слой поиска по каталогу** | В `lifespan` (FAISS index + mapping) | `index`, `id_to_slug` — read-only после старта | `index.search`, `is_wine_photo`, `sigmoid_f1_score` |
| **Слой извлечения карточки** | — | Без состояния | `find_by_slug`, `somelier`, `fetch_wine_data` |
| **Доп. функции** | При старте (лента) | TTL-кэш в памяти процесса (`_feed_cache_*`) | лента, debug-кроп, тестовый эндпоинт |

Граница между слоями — это граница ответственности, а не модульная граница на уровне файлов: все они вызываются друг из друга напрямую как обычные Python-функции, без интерфейсов и DI. Это упрощает код, но означает, что рефакторинг в отдельные модули потребует ручного выделения этих границ.

```
API-слой
  │  (HTTP-запрос → распаковка Pydantic-модели)
  ▼
Нормализация
  │  (сырые байты → готовый тензор для модели)
  ▼
ML-слой (признаки)
  │  (изображение → embedding)
  ▼
Слой поиска по каталогу
  │  (embedding → wine_id / slug)
  ▼
Слой извлечения карточки
  │  (slug → полные данные о вине)
  ▼
API-слой
     (данные → JSON-ответ)
```

## 3. Нормализация фото

Цель слоя — привести произвольное входное изображение к строго фиксированному формату, ожидаемому YOLO-моделью, без искажения пропорций.

### 3.1. Декодирование входа

```
image_base64 (возможно с data:-префиксом)
  → data.image_base64.split(",")[-1]   # отбрасывается префикс "data:image/...;base64,"
  → base64.b64decode(...)
  → PIL.Image.open(io.BytesIO(...)).convert("RGB")
```

Результат — `PIL.Image` в RGB, независимо от исходного цветового режима (например, RGBA или CMYK).

### 3.2. Letterbox-препроцессинг (`letterbox_preprocess`)

YOLO-модель ожидает вход фиксированного размера 640×640. Простое сжатие исказило бы пропорции этикетки, поэтому используется letterbox:

1. PIL-изображение конвертируется в NumPy-массив и переводится из RGB в BGR (формат, ожидаемый ONNX-моделью).
2. Вычисляется единый коэффициент масштабирования `scale = min(640/h, 640/w)`, сохраняющий пропорции.
3. Изображение масштабируется по этому коэффициенту (`cv2.resize`).
4. Оставшееся пространство до 640×640 заполняется серым паддингом (`114, 114, 114` по каждому каналу) симметрично по краям.
5. Массив нормализуется в диапазон `[0, 1]` (`/255.0`) и транспонируется в формат `NCHW` (`(1, 3, 640, 640)`), ожидаемый ONNX Runtime.

Функция возвращает не только сам тензор, но и `scale` и `(dw, dh)` — параметры, необходимые позже, чтобы перевести предсказанный bounding box обратно в координаты исходного (немасштабированного) изображения.

### 3.3. Обрезка по этикетке (или fallback)

После получения bounding box от YOLO (см. раздел 4) нормализация завершается фактическим кропом:

* если этикетка обнаружена с уверенностью выше порога — исходное `PIL.Image` обрезается по вычисленным границам (`image.crop(...)`);
* если нет — в DINOv2 передаётся исходное, необрезанное изображение целиком.

Таким образом, "нормализованное" изображение, поступающее на вход экстрактору признаков, — это либо этикетка крупным планом, либо всё фото, но всегда единый `PIL.Image` в RGB без привязки к исходному разрешению.

## 4. Извлечение признаков

Слой превращает нормализованное изображение в вектор фиксированной размерности, пригодный для сравнения в каталоге. Состоит из двух моделей, выполняемых последовательно.

### 4.1. YOLO — детекция этикетки

* Модель: `label_detector.onnx`, инференс через `onnxruntime` (`CPUExecutionProvider`).
* Вход: тензор `(1, 3, 640, 640)` из letterbox-препроцессинга.
* Выход: массив предсказаний, приводится к форме `(N, 5+)`, где по каждой детекции берутся координаты `xc, yc, w, h` (в долях от 640) и confidence-скоры по классам.
* Выбирается детекция с максимальным confidence (`np.argmax(scores)`).
* Если `best_score > 0.25` (`YOLO_CONFIDENCE_THRESHOLD`):
  1. координаты `xc, yc, w, h` переводятся из формата XYWH в XYXY в пространстве модели (640×640);
  2. вычитается паддинг (`dw, dh`) и результат делится на `scale`, возвращая координаты в пространство исходного изображения;
  3. координаты клипуются в границы `[0, orig_w] × [0, orig_h]`;
  4. `box_detected = True`.
* Если уверенность ниже порога — bounding box не строится, `box_detected = False`, используется всё изображение.

`box_detected` — важный флаг, который передаётся дальше в слой поиска по каталогу и влияет на выбор порога similarity (раздел 5).

### 4.2. DINOv2 with Registers — embedding

* Модель: `facebook/dinov2-with-registers-small`, загружается через `transformers.AutoImageProcessor` + `AutoModel`.
* Вход: (кроп этикетки либо полное фото) — `PIL.Image`, препроцессится штатным `AutoImageProcessor` модели (ресайз/нормализация под конкретный чекпойнт, независимо от letterbox-шага YOLO).
* Инференс выполняется в `torch.inference_mode()` на `device` (CUDA, если доступна, иначе CPU — определяется один раз при старте процесса).
* Агрегация в единый вектор управляется переменной окружения `EMBEDDING_MODE`:
  * `cls` (по умолчанию) — берётся `outputs.pooler_output[0]`;
  * `mean` — берётся среднее по patch-токенам `outputs.last_hidden_state[0, 1 + num_registers:]` (CLS-токен и register-токены отбрасываются).
* Итоговый вектор L2-нормализуется (`F.normalize(..., p=2, dim=0)`) — это условие корректности последующего поиска по cosine similarity через `IndexFlatIP`.
* Результат приводится к `float32` NumPy-массиву размерности 384 (`hidden_size` модели).

### 4.3. Инвариант размерности

При старте приложения (`lifespan`) проверяется, что `index.d == embedding_dimension` — размерность FAISS-индекса обязана совпадать с размерностью, которую реально выдаёт DINOv2. Несовпадение приводит к `RuntimeError` и остановке старта сервиса, а не к тихой деградации качества поиска.

## 5. Поиск по каталогу

Слой превращает embedding в конкретный `wine_id`, принимая решение о том, достаточно ли уверенно совпадение, чтобы считать фото распознанным вином.

### 5.1. FAISS-поиск

* Индекс: `IndexFlatIP` (inner product), загружается один раз при старте из `wines_base.index` — сервис не пишет в индекс, только читает (read-only база, предвычисленная офлайн).
* Поскольку все векторы (и индекса, и запроса) L2-нормализованы, inner product эквивалентен cosine similarity.
* Запрос: `index.search(embedding.reshape(1, -1), k=5)` — возвращает top-5 ближайших векторов с их similarity-скорами.
* Для каждого из top-5 кандидатов вычисляется:
  * `slug` — через `id_to_slug.get(int(idx), "unknown")` (mapping `FAISS id → slug`, загруженный из `wines_mapping.json`);
  * `f1_score` — сигмоидальная нормализация похожести (раздел 5.3).

### 5.2. Двухуровневая фильтрация "это распознанное вино?"

Каталоговый поиск возвращает кандидата всегда (FAISS не умеет отвечать "ничего не найдено"), поэтому решение о том, доверять ли top-1, принимается двумя последовательными фильтрами:

1. **Адаптивный порог `is_wine_photo(similarity, box_detected)`**
   ```
   threshold = SIMILARITY_THRESHOLD_WITH_BOX  (0.45)  если этикетка обнаружена
             = SIMILARITY_THRESHOLD_NO_BOX    (0.55)  если этикетка НЕ обнаружена
   similarity >= threshold → True
   ```
   Логика: если YOLO уверенно локализовал этикетку, для распознавания достаточно меньшей похожести, чем при поиске по всему кадру, где фон и посторонние объекты размывают embedding.

2. **Абсолютный порог `similarity < 0.7`** — применяется поверх первого фильтра, независимо от `box_detected`. Отсекает случаи, формально прошедшие адаптивный порог, но с top-1 похожестью ниже уровня, который на практике считается надёжным совпадением.

Оба фильтра завершаются `HTTPException(404)`, но с разными сообщениями клиенту — это позволяет клиенту различать "на фото вообще не вино" и "похоже на вино, но точного совпадения в базе нет".

### 5.3. Сигмоидальный F1-score

```python
f1 = 1 / (1 + exp(-k * (similarity - s0))),   s0 = 0.70,  k = 15.0
```

Сырая cosine similarity (диапазон `[-1, 1]`, реально наблюдаемые значения — узкий верхний поддиапазон) плохо интерпретируется как "уверенность". Сигмоида с центром в `s0 = 0.70` даёт резкий переход около порога отсечения и превращает similarity в более наглядную 0…1-метрику, которая возвращается клиенту как в топ-1 (`metrics.top1_f1`), так и по каждому из top-5 кандидатов (`metrics.top5_candidates[].f1_score`).

### 5.4. Выход слоя

На выходе — `wine_id` (int, ключ FAISS), `similarity` (top-1, float), `box_detected` (bool) и `metrics` (словарь с top-5 кандидатами и F1-скорами). `wine_id` далее транслируется в `slug` через тот же `id_to_slug`, уже во входной точке слоя извлечения карточки.

## 6. Извлечение карточки

Слой не хранит данные о винах сам — при каждом запросе он "на лету" забирает их со стороннего сайта-каталога `vino-svoe.ru` по уже известному `slug`. Состоит из двух независимых HTML-парсеров, объединяемых в `fetch_wine_data`.

### 6.1. `find_by_slug(slug)` — основная карточка

```
GET https://vino-svoe.ru/wines/{slug}
  → BeautifulSoup(html.parser)
  → извлечение по CSS-классам:
       description  ← p.wine-page__description
       wine_name    ← h1.wine-main-title-block__title
       factory      ← a.wine-main-title-block__manufacturer
       rate         ← span.wine-main-title-block__rating-text
       atcc_list    ← [p.wine-detail-info__detail-value]  (регион/сорт/тип/цвет)
       num_list     ← [p.wine-hero-block__card-value]     (температура/крепость)
       dishes_list  ← [p.wine-dish-item__name]
       wine_image   ← img.wine-hero-block__bottle → отдельный GET → base64
```

Изображение бутылки не проксируется по ссылке, а скачивается сервером синхронно и встраивается в ответ как `data:image/jpeg;base64,...` — клиенту не нужно делать дополнительный запрос к стороннему сайту.

### 6.2. `somelier(slug)` — рекомендации

Парсит блок "похожих вин" на той же странице (`a.wine-item`, лимит 5 карточек): для каждой карточки извлекается название, ссылка на рекомендованное вино и её изображение (скачивается и кодируется как `data:image/webp;base64,...`). Если блока рекомендаций нет или парсинг не дал результатов — возвращаются 5 плейсхолдеров `["Нет информации", "Нет картинки", ""]`.

### 6.3. `fetch_wine_data(wine_id)` — точка сборки

```
wine_id
  → id_to_slug[wine_id] → slug
  → find_by_slug(slug)  → (url, slug, description, name, factory, rate, atcc, num, dishes, image)
  → somelier(slug)      → recommended_wines
  → единый кортеж → parsed_info() → JSON-ответ
```

### 6.4. Отказоустойчивость извлечения

Оба парсера не пробрасывают сетевые/парсинговые исключения наружу: при любой ошибке (недоступность сайта, изменение вёрстки, таймаут) все текстовые поля подставляются заглушками (`"Не удалось загрузить информацию"`, `"Ошибка подключения к сайту"`), а `wine_image` — строкой `"Нет картинки"`. Это гарантирует, что API-слой всегда получает структурно валидный кортеж и возвращает `200`, даже если сторонний сайт временно недоступен — ценой того, что клиент не получает явного сигнала об этой деградации.

## 7. Дополнительные функции

### 7.1. Винная лента (`GET /feed`)

Независимый от основного пайплайна функционал, работающий поверх тех же данных (`vino-svoe.ru`, `wines_mapping.json`), но без ML-слоя:

```
_feed_cache_bytes / _feed_cache_timestamp / _feed_cache_lock
  │
  ├── кэш валиден (< 6 часов)?  → мгновенный ответ из памяти
  │
  └── кэш невалиден
        → asyncio.Lock (double-checked locking)
        → _build_feed_response() в отдельном потоке (asyncio.to_thread)
              ├── _load_feed_news()   — параллельный обход 7 разделов сайта,
              │                          дедупликация, сортировка по дате,
              │                          гарантированное представительство
              │                          каждого раздела + добор свежими
              │                          статьями до FEED_NEWS_LIMIT=20
              └── _load_feed_wines()  — до FEED_WINE_LIMIT=30 slug'ов из
                                         wines_mapping.json, лёгкая версия
                                         find_by_slug() без описания/рекомендаций
        → если сборка упала и есть старый кэш → отдать его (X-Feed-Cache: stale)
        → если кэша никогда не было → 500
```

### 7.2. `/api/memory` — карточка по известному slug

Пропускает слои нормализации/признаков/поиска целиком: сразу вызывает `find_by_slug` + `somelier` по переданному `memory_slug`. Используется, когда клиент уже знает slug вина (например, открывает ранее распознанную карточку повторно) и не хочет повторно платить за ML-инференс.

### 7.3. `/api/test_for_slug` — тестовый эндпоинт пайплайна

Задуман как способ прогнать полный пайплайн (нормализация → признаки → поиск) и получить в ответ только `slug`, без похода в слой извлечения карточки — удобно для валидации качества распознавания без нагрузки на парсинг сайта. Принимает изображение тремя альтернативными способами (`UploadFile`, form-поле `image_base64`, сырое тело запроса), однако вызывает неопределённую в модуле функцию `process_and_convert_to_base64` — в текущем состоянии кода эндпоинт нерабочий (см. также раздел 8).

### 7.4. Debug-кроп (`save_crop_for_debugging`)

Не участвует в основном ответе клиенту, но подключена к общему пайплайну для отладки качества YOLO-кропа: при `DEBUG_SAVE_CROPS = True` сохраняет обрезанное изображение на диск (`debug_crops/`) и дублирует его как base64 в лог-поток чанками по 4000 символов, с маркерами `[DEBUG_CROP_BASE64_START]`/`[DEBUG_CROP_BASE64_END]`.

## 8. Сквозные архитектурные наблюдения

* **Слой поиска по каталогу read-only во время работы сервиса.** И FAISS-индекс, и mapping загружаются один раз в `lifespan` и не изменяются — обновление каталога требует пересборки `wines_base.index`/`wines_mapping.json` офлайн и перезапуска процесса.
* **Слой извлечения карточки — единственная точка сетевой зависимости от стороннего сайта.** Именно здесь сервис хрупок к изменению вёрстки `vino-svoe.ru`; ни нормализация, ни извлечение признаков, ни поиск по каталогу от внешнего сайта не зависят.
* **PostgreSQL не входит ни в один из описанных слоёв.** Инфраструктура подключена (`psycopg2-binary`, `init.sql`), но в текущем пайплайне не используется — реальный mapping `id → slug` живёт в `wines_mapping.json`, а не в БД.
* **`/api/test_for_slug` не завершает пайплайн исправно** — единственная точка входа, где нормализация/признаки/поиск теоретически доступны без извлечения карточки, содержит неопределённую зависимость (`process_and_convert_to_base64`) и требует исправления перед использованием.
